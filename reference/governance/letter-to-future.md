# 給未來 Session 的信

> 2026-07-04，由 Fable 5 寫於制度建置 session 尾聲。讀者是之後每一個接手的模型——多半是 Sonnet 5。
> 這封信不是規則（規則在其他檔），是規則以外我認為最重要、但使用者沒問的事。

## 一、三件沒被問到、但最重要的事

**1. 這套制度死於不被載入，不死於寫錯。**
governance/ 寫得再好，若 session 裡沒人讀就等於不存在。唯一可靠的載入面是常載層
（兩層 CLAUDE.md＋core-rules＋MEMORY.md），所以行數預算是整套制度的命脈——
每多一行常載雜訊，關鍵規則被淹沒的機率就高一分。守住 maintenance §3 的上限，
比再寫十份新文件更有價值。同理：例外會累積。「這次趕時間先直接做」的第三次，制度就名存實亡；
把「Agent 呼叫缺 model」當 bug 修（而非風格建議），是防線的第一塊磚。

**2. 驗證閘門是 vault 複利的本錢。**
這個 vault 的價值在於它可信到能拿來回答醫療問題。捏造債（fabrication debt）比知識複利更快——
一條假引用被下游三篇 note 引用後，清理成本是攔截成本的十倍以上。2026-07-04 的 refs=0 fidelity gate
攔到憑空捏造的人名，證明「來源薄的地方加抽查閘門」這個模式有效；請把它推廣到所有來源薄的場景
（refs=0、abstract-only stub、OCR 品質差的 raw），而不是只留在 EMCrit 管線。
記住：沒有 artifact 證據的 PASS，是全系統最貴的 token。

**3. 模型經濟有半衰期，每季重估。**
這次改制度的直接誘因之一是 Sonnet 5 出現——near-Opus 能力、0.6 倍價格，讓「主對話用 Opus」
一夜過時。同樣的事還會發生：今天的層級表（haiku→sonnet→opus）是 2026-07 的快照，不是真理。
maintenance §4 的季度稽核不是官樣文章，第一個到期日 2026-08-31（Sonnet 5 促銷結束）就會考驗你們
會不會真的跑它。查證的方法已經內建（claude-api skill 離線可查），沒有藉口憑記憶。

## 二、這套制度最可能的退化方式與預防

| 退化模式 | 早期徵兆 | 預防（已內建的機制） |
|---|---|---|
| 常載層回胖 | CLAUDE.md／core-rules 被「順手加一條」 | maintenance §3 行數上限＋紅區先問；加新規則的正確位置是 governance 本文，不是常載層 |
| 驗證劇場 | 回報有 PASS 沒有 `檔案:行號` | 回報合約（dispatch §4）明定無證據＝不採信；裁決端照 R2 checklist 走 |
| 升級棘輪 | 「保險起見」小事也派 opus | 升級必附失敗軌跡（dispatch §5）——湊不出軌跡的升級自然被擋下 |
| 範本與現實脫節 | skill／工具改名後範本還寫舊名 | 季度稽核第 3 項路徑健檢；踩到就照 maintenance §2 記教訓 |
| 停車場變垃圾場 | NEXT_SESSION 停車場 >10 條沒人動 | 每次 session-handoff 順手掃一眼：能三行內做完的做掉，過時的刪，其餘保留 |
| 教訓只進 memory 不進制度 | 同一坑第二次踩 | maintenance §2 第 2 步：改變調度／驗證行為的教訓，必須在對應 governance 檔留一行索引 |

## 三、誠實：這次產出中我信心最低的部分

1. **交辦門檻與升降級次數是啟發式，不是量測值。**「>2 檔／>400 行／≥3 處」「haiku 錯 1 次升級」
   這些數字沒有本地 telemetry 支撐（週報目前只量件數）。用起來若覺得太敏感（頻繁升級浪費）或
   太鈍（重工），直接改數字並照 maintenance §2 記一行——數字是初值，機制才是重點。
2. **Sonnet 5 能否穩定執行全部 rubric，未實測。**maintenance §5 第 1 項冒煙測試就是為了補這個洞。
   若發現某條 rubric 在 Sonnet 上系統性被誤讀，優先改寫那條的措辭（更機械、更多例子），不是升級模型。
3. **內建 agent（Explore／Plan 等）的預設 model 行為，官方文件沒寫。**制度用「一律顯式帶 model」
   繞過，但若哪天 harness 改了參數語義，速查卡第 1 條要跟著驗一次。
4. **Fable→Opus 4.8 導流的額度歸屬未確認**（官方未載明）。已標在 dispatch §8；只在再次用到 Fable 時重要。
5. **對抗審查的覆蓋有限。**收尾的 fresh-context 審查只跑了有限輪次，規則間更隱微的矛盾可能仍在。
   發現矛盾時：兩條規則都先不改，提使用者裁決（紅區程序），裁決結果記入教訓段。
6. **診斷 #1〜#3 的排序是判斷，不是量測。**依據是 memory 中事故的頻率與代價印象；若日後有 telemetry
   顯示別的洞更大，重排 diagnosis.md 即可，不必忠於這次的排序。
